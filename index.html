📘
Overview — What is Edit Distance?
Start here ▼

The Levenshtein Distance (edit distance) between two strings is the minimum number of single-character operations needed to transform one string into another. It was introduced by Soviet mathematician Vladimir Levenshtein in 1965.

Dynamic Programming computes it in O(mn) time using a table d[i, j] — where d[i, j] represents the edit distance between the first i characters of the source string and the first j characters of the target string. The recurrence considers three operations: insert (d[i, j−1] + 1), delete (d[i−1, j] + 1), and replace/match (d[i−1, j−1] + cost). Reference: Cormen et al., Introduction to Algorithms, Problem 15-5. See also: Wikipedia — Edit Distance.

The three allowed operations are:

OperationArrowFormulaPlain EnglishCost
Match ↖ d[i-1][j-1] + 0 S[i] = T[j] already — do nothing 0
Substitute ↖ d[i-1][j-1] + 1 Replace S[i] with T[j] 1
Insert ← d[i][j-1] + 1 Insert T[j] into source 1
Delete ↑ d[i-1][j] + 1 Delete S[i] from source 1

The recurrence relation (the heart of the algorithm):

d[0][0] = 0 d[i][0] = i (delete i chars to reach empty string) d[0][j] = j (insert j chars from empty string) d[i][j] = d[i-1][j-1] if S[i] = T[j] ← FREE match d[i][j] = 1 + min( d[i][j-1], ← insert T[j] d[i-1][j], ↑ delete S[i] d[i-1][j-1] ) ↖ substitute

When to use it:

🔤 Spell checkers 🧬 DNA alignment 🔍 Fuzzy search 📋 Diff tools 🛡 Plagiarism detection 📱 Autocorrect 🌐 Natural language processing 📦 Version control
💡 Key insight: We never need to check all possible edit sequences. Dynamic Programming guarantees we find the global optimum by building on already-solved subproblems — each cell d[i][j] is computed exactly once in O(1) time.
⚙
How It Works — The Algorithm Step by Step
Algorithm ▼

The algorithm has three phases. Each phase maps directly to pseudocode lines highlighted during animation:

1
Initialization — Fill base cases (lines 3–5)
Create an (m+1)×(n+1) table. Set d[i][0] = i for all i (cost of deleting i source chars) and d[0][j] = j for all j (cost of inserting j target chars). These are the only cells with known answers before the DP starts.
2
Fill — Compute every cell row-by-row (lines 6–13)
For each pair (i, j), compare S[i] with T[j]. If they match, inherit the diagonal (free). Otherwise take the minimum of insert (←), delete (↑), or substitute (↖) — each costs 1 more than its source cell. This is the DP recurrence. The table fills left-to-right, top-to-bottom.
3
Traceback — Recover the optimal edit sequence (line 14)
Starting at d[m][n], follow predecessors backwards to d[0][0]. At each cell, choose the neighbour that produced the minimum — diagonal (match/sub), left (insert), or above (delete). This path is the optimal sequence of edits. Traceback runs in O(m+n) time.
⏱ Complexity: Time = O(m×n) — we fill every cell exactly once. Space = O(m×n) for the full table, or O(min(m,n)) if only the distance is needed (rolling rows). There is no best-case shortcut — every cell must be computed.

Key Concepts — Important Ideas to Understand
6 concepts ▼

✅ Optimal Substructure

d[i][j] depends only on three already-solved subproblems: d[i-1][j-1], d[i-1][j], d[i][j-1]. The optimal solution to the full problem is built from optimal solutions to smaller problems.

🔁 Overlapping Subproblems

Without memoization, naive recursion recomputes d[2][3] hundreds of times. DP stores each result exactly once — reducing O(3mn) to O(mn). This is why DP is needed.

↔ Symmetry Property

dist(S, T) = dist(T, S). Swapping source and target always gives the same edit distance. The table transposes but the answer is identical.

💾 Space Optimization

When only the distance is needed (not the path), you only need the previous row. Space drops from O(mn) to O(min(m,n)) using two rolling arrays.

📐 Metric Properties

Edit distance is a true metric: non-negative, symmetric, and satisfies the triangle inequality dist(A,C) ≤ dist(A,B) + dist(B,C). This enables clustering and nearest-neighbour search.

🔄 Multiple Optimal Paths

There may be several edit sequences achieving the minimum cost. The traceback finds one valid path — a different tie-breaking rule could produce a different but equally valid sequence.

⚠
Common Mistakes — What Students Get Wrong
4 mistakes ▼

⚠ Mistakes to Avoid

❌ Wrong

Off-by-one indexing. Using S[i] and T[j] directly when S and T are 0-indexed. The table is 1-indexed — d[i][j] uses S[i-1] and T[j-1].

✅ Correct

Always access S[i-1] and T[j-1] inside the loop. The table has an extra row/column of base cases at index 0.

❌ Wrong

Forgetting base cases. Starting the fill loop at i=0 or j=0 without initialising the border first. d[i][0] and d[0][j] must be set before the main loop.

✅ Correct

Always initialise: d[i][0]=i for all i, and d[0][j]=j for all j, before entering the double loop.

❌ Wrong

Using cost=1 on a match. Setting cost=1 when S[i-1]=T[j-1]. A match is free — cost must be 0, otherwise the diagonal is penalised incorrectly.

✅ Correct

cost = (S[i-1] === T[j-1]) ? 0 : 1. Only the substitute operation has a cost — a match uses the same diagonal value unchanged.

❌ Wrong

Greedy traceback. Always choosing diagonal first during traceback. A greedy rule can pick a suboptimal path even when insert or delete would lead to fewer total operations.

✅ Correct

At each traceback cell, check all three predecessors and follow the one whose value equals the current cell's value minus the operation cost. Don't assume diagonal is always best.

Why Is It Always O(mn)? — The Key Insight
📐
Table Size
The DP table has (m+1) × (n+1) cells. For m=6, n=7 that's 56 cells — every single one must be computed, no exceptions.
⚡
Each Cell = O(1)
Computing d[i][j] is just one comparison and one min(a,b,c) — three lookups, one math operation. Constant time regardless of string content.
🚫
No Early Exit
Unlike search algorithms, there is no condition that lets us stop early. Even if strings are identical, d[m][n]=0, we still fill every cell to prove it.
🔢
Total Work
Total = (m+1)×(n+1) × O(1) = O(mn). Best = Worst = Average. This is denoted Θ(mn) — tight upper and lower bound.

Sorting & Searching — The min() Choice & Traceback Path Search

At every cell, we search for the minimum among 3 candidates. The traceback is a path search through the filled DP table.

🔍 The Core Search: min(insert, delete, replace) at Every Cell

At each cell d[i][j], the algorithm performs a 3-way comparison search — it evaluates all three possible edit operations and selects the one with the minimum cost. This is the fundamental searching step that runs O(mn) times.

🔍 Traceback — Path Search Through the DP Table

After filling the table, the traceback performs a greedy path search starting at d[m][n] and walking backwards to d[0][0]. At each step it searches the three predecessors and follows the one whose value equals the current cell minus the operation cost — this is equivalent to finding the shortest path on a DAG.

The traceback runs in O(m+n) time — at most m+n steps since each step moves at least one index closer to (0,0). The green path in the visualization shows this search result.

Impact Analysis — What Happens Without the min() Search?

With the min() search at every cell: we always find the globally optimal edit distance. The search evaluates insert, delete, and replace costs and picks the cheapest — guaranteeing the minimum over all possible edit sequences.

Design Paradigm — Dynamic Programming

Edit Distance is solved using Dynamic Programming. It satisfies both DP conditions: optimal substructure and overlapping subproblems.

Algorithm Paradigm Dynamic Programming (Bottom-Up)
✅ Optimal Substructure ✅ Overlapping Subproblems ❌ Not Greedy ❌ Not Divide & Conquer
① Optimal Substructure

The solution to d[i][j] is built from optimal solutions to three smaller subproblems:

  • d[i][j-1] — best way to align S[0..i] with T[0..j-1]
  • d[i-1][j] — best way to align S[0..i-1] with T[0..j]
  • d[i-1][j-1] — best way to align S[0..i-1] with T[0..j-1]

The globally optimal solution contains optimal sub-solutions. This guarantees that building the table bottom-up produces the correct answer.

② Overlapping Subproblems

In naive recursion, the same cell d[i][j] is computed many times from different recursive paths. Example: computing d[3][3] naively requires d[2][2], which itself requires d[1][1] — but d[1][1] is also needed by d[2][1], d[1][2], etc.

The DP table stores each result exactly once, reducing exponential O(3mn) to polynomial O(mn).

Counterexample — Why Greedy Fails Greedy ✗

Greedy makes the locally best choice at each step — but local optimality does NOT guarantee global optimality for edit distance.

❌ Greedy: "abc" → "cab"
abc → cab
Step 1: 'a'≠'c', sub → cbc (+1)
Step 2: 'b'≠'a', sub → cac (+1)
Step 3: 'c'≠'b', sub → cab (+1)
Greedy cost: 3
✅ DP Optimal: "abc" → "cab"
abc → cab
Step 1: insert 'c' → cabc (+1)
Step 2: delete 'c' → cab (+1)

DP cost: 2

Greedy cost: 3. DP cost: 2. Greedy missed the globally cheaper insert+delete strategy because it only looked one step ahead.

DP Table Fill Order & Dependencies

The table fills row by row, left to right (bottom-up). When computing d[i][j], all three predecessors are already available:

d[i][j] depends on: d[i-1][j-1] ↖ diagonal (previous row, previous col — match/sub) d[i-1][j] ↑ above (previous row, same col — delete) d[i][j-1] ← left (same row, previous col — insert)

This bottom-up fill order guarantees correct topological ordering of the dependency graph in O(mn) time with no recursion needed.
