🔤 Edit Distance — Overview ▼
Core Idea

Given two strings S and T, find the minimum number of single-character edits — insertions, deletions, or substitutions — to transform S into T. The answer is stored in the bottom-right cell of a DP table.

How It Works (Step by Step)
1. Create a (m+1)×(n+1) table. Fill row 0 with 0,1,2…n and column 0 with 0,1,2…m.
2. For each cell d[i][j], check if S[i] equals T[j]. If yes — free diagonal move (match). If no — pay 1 for substitute.
3. Take the minimum of three candidates: d[i][j-1]+1 (insert ←), d[i-1][j]+1 (delete ↑), d[i-1][j-1]+cost (replace/match ↖).
4. Fill the table row by row. When done, d[m][n] is the minimum edit distance.
5. Traceback: Walk backward from d[m][n] to d[0][0] following minimum-cost predecessors to recover the exact edit sequence.
6. If a pass fills with all matches (cost 0), the strings are identical — distance = 0.
Complexity
Time: Θ(mn) | Space: O(mn) full table | Optimised: O(n) space | Stable: ✓ Deterministic
When to Use

Autocorrect, spell checking, DNA alignment, git diff, and fuzzy search. Any task requiring approximate string matching — finding how similar two sequences are. Not efficient for very long strings without the space-optimised variant.

Concept

What is Time Complexity?

Time complexity tells us how the number of operations grows as the input size grows. We use Big-O notation to describe this growth — for example, O(n²) means the operations grow proportional to n squared.

For Edit Distance, the input size is the length of the two strings. If the source string has m characters and the target has n characters, then the DP table has (m+1) × (n+1) cells — and every single one must be filled.

Why is Edit Distance always Θ(mn)?

Unlike many algorithms, Edit Distance has no best case. Even if the two strings are identical ("abc" → "abc"), the algorithm must still fill every cell to confirm that the distance is zero. There is no shortcut, no early exit, no pruning.

💡 Intuition

Think of filling a grid. If the grid has m rows and n columns, you must visit every square — no matter what the values are. That is exactly what happens here. (m+1)×(n+1) cells × O(1) work per cell = Θ(mn) total.

The Θ symbol (Theta) means this is a tight bound — the algorithm is never faster or slower than mn in any case. This is different from O (which only gives an upper bound).

Concept

What is Memoization and why does it matter?

Both the naive recursive approach and the DP approach solve exactly the same problem with exactly the same logic. The only difference is: does the algorithm remember answers it has already computed?

The naive approach does not remember — it recomputes the same sub-problem every time it is needed. The DP approach stores each answer in a table and looks it up in O(1). This single difference changes the runtime from billions of operations to hundreds.

📌 Key Insight

When computing d[3][3], both approaches also need d[2][2]. The naive approach computes d[2][2] fresh every time. The DP approach computed d[2][2] earlier and just reads it from the table. For large strings, d[2][2] might be recomputed millions of times by the naive approach.

The numbers — how bad is naive recursion?

For strings of length n (equal length), the naive approach makes up to 3n recursive calls. This grows faster than any polynomial:

    naive(i-1,j),  ← delete
    naive(i-1,j-1)) ← replace

⚠ Why naive is so slow

Both approaches make the same 3 recursive calls. But naive recursion recomputes d[i][j] every time it is needed — exponentially many times. DP computes each cell exactly once and stores it. This is the definition of overlapping subproblems — the core reason DP exists.

Why Θ(mn) with no exceptions

The DP table has (m+1)×(n+1) cells. Each takes O(1) to compute: one character comparison and one min(a,b,c). Total = Θ(mn) exactly. No early exit, no pruning, no best case. This is why the bound is Θ (tight) rather than just O (upper bound).

Concept

What triggers the worst case?

For Edit Distance DP, the worst case occurs when no characters match between source and target. In this situation, every single cell must evaluate all three operations (insert, delete, replace) and select the minimum — no shortcuts are possible.

Example: "aaaaab" → "bbbbba". Not a single character aligns positionally, so every cell in the table does the maximum amount of work. The resulting edit distance equals max(m, n) — you need to replace every character.

Despite this extra work per cell, the overall complexity remains Θ(mn). The worst case changes the distance value, not the number of cells filled.

Concept

What is Dynamic Programming?

Dynamic Programming is a problem-solving strategy for situations where a large problem can be broken into smaller overlapping sub-problems. Instead of solving the same sub-problem over and over, you solve it once, remember the answer, and reuse it whenever it comes up again.

Think of it like this: if you are walking up a staircase and you want to know the cheapest path to step 10, you don't need to re-examine steps 1–9 every time. You computed those costs already. DP is the discipline of writing down intermediate results so you never do the same work twice.

💡 Concrete analogy

Imagine computing Fibonacci numbers by hand: F(5) = F(4) + F(3). If you compute F(4) first, it internally computes F(3) — and then you compute F(3) again for the second part. Without DP you do this exponentially many times. With DP you write down F(3) = 2 the first time and just read it back. Edit Distance works the same way — every cell d[i][j] is computed exactly once and looked up whenever a larger cell needs it.

Why is DP the right tool for Edit Distance?

Edit Distance satisfies both conditions that make DP the correct approach:

Algorithm Paradigm
Dynamic Programming (Bottom-Up)
✅ Optimal Substructure ✅ Overlapping Subproblems ❌ Not Greedy ❌ Not Divide & Conquer

① Optimal Substructure

What it means: The optimal solution to the full problem contains optimal solutions to its subproblems.

In Edit Distance: d[i][j] is built from three smaller problems: d[i][j-1] (insert ←), d[i-1][j] (delete ↑), and d[i-1][j-1] (match/sub ↖). The minimum of these gives the optimal answer for d[i][j]. If we knew the optimal answers to those three, we can find the optimal answer for d[i][j].

② Overlapping Subproblems

What it means: The same subproblems appear repeatedly when solving the main problem recursively.

In Edit Distance: Computing d[3][3] requires d[2][2], which is also needed by d[2][3] and d[3][2]. In naive recursion, d[2][2] gets recomputed many times. DP solves it once and stores the result — reducing exponential work to Θ(mn).

Top-Down vs Bottom-Up DP

There are two ways to implement DP for the same problem:

Top-Down (Memoization)

Start with the full problem and recurse. When a subproblem is solved, store its result in a memo table. If the same subproblem appears again, return the stored result instead of recomputing. This is lazy — it only computes what is actually needed.

Bottom-Up (Tabulation) — used here

Start with the smallest subproblems (the base cases) and build up systematically. Fill the entire table row by row. By the time you need d[i][j], all three of its predecessors are already computed. This is what the animation shows.

Concept

What are Overlapping Subproblems?

A problem has overlapping subproblems when solving it recursively causes the same smaller problem to be solved more than once. This is the defining characteristic that makes DP appropriate — instead of recomputing, we store.

Consider computing d[2][2] for "ab" → "ba". Naive recursion would call d[1][1] from multiple paths — once from the insert branch, once from the delete branch, once from the replace branch. DP calls d[1][1] exactly once, stores the answer, and reads it directly for all future needs.

Click Animate below to see which cells are shared dependencies when computing d[2][2]. The purple cells are needed by multiple parent calls in naive recursion — DP stores them once and reuses:

Why this transforms the complexity

For strings of length m and n, naive recursion has an exponential call tree. Each node branches into up to 3 children, and many of those subtrees are identical. DP collapses this entire tree into a flat (m+1)×(n+1) table — one computation per cell, one table lookup for all future references. This is why memoization (top-down DP) and tabulation (bottom-up DP, used here) both achieve Θ(mn) instead of O(3mn).

Concept

What is Greedy, and why doesn't it work here?

A greedy algorithm makes the locally best choice at each step — the choice that looks best right now — without considering the future consequences. Greedy algorithms are fast and simple, and they work correctly for some problems (like finding a minimum spanning tree).

However, a greedy choice can lead to a globally suboptimal solution. For Edit Distance, always substituting the current character whenever it doesn't match seems reasonable — but it misses cheaper combinations of operations that only become visible when you look ahead.

Counterexample — "abc" → "cab"

This example proves greedy fails. The correct minimum edit distance is 2, but greedy produces 3:

❌ Greedy approach
abc → cab
Step 1: 'a'≠'c' → substitute → cbc  (+1)
Step 2: 'b'≠'a' → substitute → cac  (+1)
Step 3: 'c'≠'b' → substitute → cab  (+1)
Total cost: 3
Greedy picked the locally cheapest move at each step
✅ DP optimal solution
abc → cab
Step 1: insert 'c' at front → cabc  (+1)
Step 2: delete last 'c'  → cab   (+1)

Total cost: 2
DP found the globally cheaper insert+delete strategy

Greedy cost: 3. DP cost: 2. Greedy substituted character by character, missing the globally cheaper insert+delete strategy. DP considers all three operations at every cell and picks the minimum — it always finds the true optimum.

Why not Divide & Conquer either?

Divide & Conquer splits a problem into non-overlapping independent subproblems, solves them separately, and combines the results. Edit Distance subproblems are NOT independent — d[i][j] is shared by d[i+1][j], d[i][j+1], and d[i+1][j+1]. D&C would recompute the shared parts. DP is the correct fit because it handles overlapping subproblems by storing results.

Concept

How does the DP table fill up?

The DP table fills row by row, left to right — starting from the top-left corner. This order is critical: when we compute d[i][j], we need its three predecessors to already be available. Let's see why this order guarantees that:

d[i][j] depends on: d[i-1][j-1] ↖ diagonal — previous row, previous col (match/substitute) d[i-1][j] ↑ above — previous row, same col (delete) d[i][j-1] ← left — same row, previous col (insert) Fill order: row by row, left to right (bottom-up tabulation). When we reach d[i][j], all three of its predecessors are already computed.

If we filled the table in any other order — say, column by column, or bottom to top — some predecessors would not be ready yet and the table would contain wrong values.

What are Base Cases, and why are they essential?

Base cases are the known starting values that the rest of the table builds on. Without them, the first row and column would reference undefined values — and those errors would propagate through the entire table.

d[i][0] = i  (column 0 — the entire left edge)

What it means: The cost of transforming the first i characters of the source into an empty string.

Why: The only way to reach the empty string is to delete all i characters, one by one. Each deletion costs 1, so d[i][0] = i.

Example: d[3][0] = 3 means: delete "kat" (3 chars) → "" costs 3 operations.

d[0][j] = j  (row 0 — the entire top edge)

What it means: The cost of transforming an empty string into the first j characters of the target.

Why: Starting from nothing, the only way to build the target is to insert every character. Each insertion costs 1, so d[0][j] = j.

Example: d[0][3] = 3 means: "" → "sat" (3 chars) costs 3 insertions.

Concept

What happens if you remove a key step?

The best way to understand why each part of the algorithm is necessary is to see what breaks when you remove it. The three scenarios below remove one component at a time and show the consequences.

SCENARIO 1 Remove the Traceback

What the traceback does: After the DP table is fully filled, the traceback searches backward from the bottom-right cell d[m][n] to d[0][0], following the minimum-cost predecessor at each step. This reconstructs the exact sequence of insert, delete, and substitute operations.

❌ Without Traceback

You get only the number — e.g. "distance = 3". You know how many operations are needed but have no idea which operations they are or in what order to apply them.

The traceback follows the path of minimum-cost moves: at each cell, ask "which predecessor gave me this value?" Move there. Repeat until d[0][0]. The path gives you the exact edit sequence.

The traceback is a path search through the DP table. At each cell it asks: "which of my three predecessors — left (insert), above (delete), or diagonal (match/sub) — gave me this minimum?" It searches until it reaches d[0][0]. Without this search, the table gives you a distance but no edit sequence — the algorithm is half-complete.

Row 0 and column 0 are the only cells whose values we know without needing predecessors. Every other cell builds on them. Without these anchors, the bottom-up computation has no valid starting point and every cell inherits undefined values.

🔤 ① What is Edit Distance? ▼
Definition

What is it?

Imagine you typed "teh" and your phone corrected it to "the". How did it know? It measured the Edit Distance — the minimum number of single-character changes needed to turn one string into another.

Edit Distance (also called Levenshtein Distance) was introduced by Vladimir Levenshtein in 1965. It is one of the most widely used algorithms in computing.

Why does it matter?

Any time software needs to compare strings approximately — rather than requiring an exact match — Edit Distance is likely involved:

🔤
Autocorrect — computes the distance from your typo to every word in the dictionary and suggests the closest one ("teh" → "the", distance = 1).
🔍
Spell checkers — "Did you mean…?" suggestions are words within distance 1 or 2 from what you typed.
🧬
DNA alignment — a gene mutation is exactly an insert, delete, or substitute operation on a DNA sequence.
📋
Git diff — shows the minimum set of line changes between two file versions.
🌐
Fuzzy search — finds near-matches even when the query is slightly misspelled.

The three operations (each costs exactly 1)

You can only make three types of changes. Any transformation is built from some combination of these:

Quick example: "teh" → "the" (answer = 1)

Source = teh, Target = the. What is the minimum number of operations?

Option 1 — substitute each wrong character:
teh → thh → the → ... this approach takes 2 operations ❌
Option 2 — delete the misplaced 'e':
teh → th → the ... wait, we still need to add 'e' back = 2 ops ❌
Option 3 — DP finds the optimal path:
teh → delete 'e' at position 2 → the = 1 operation ✓
💡 Key insight

The trick is that deleting 'e' from position 2 makes 'h' slide into position — and 'e' is already at position 3. The naive approach misses this. DP finds it because it considers all possible combinations of operations systematically.

⚙ ② How Does the Algorithm Work? ▼
Step-by-Step

The big idea: solve small, build up

Instead of asking "how do I transform the whole word?", the algorithm asks a much simpler question: "how do I transform just the first few characters?" It answers this for every possible prefix pair, then uses those answers to answer larger ones.

This builds up a table where each cell d[i][j] stores one sub-answer:

What does d[i][j] mean?

d[i][j] = the minimum edit distance between the first i characters of the source and the first j characters of the target.

For example, with source = "kitten" and target = "sitting": d[3][4] answers "what is the minimum cost to transform kit into sitt?" — a smaller, manageable version of the full problem.

By the time the algorithm reaches the bottom-right corner, it has solved every sub-problem on the way there. The final answer sits in cell d[m][n]. No extra work needed — it was built up incrementally.

Why not just try every possible sequence of operations?

There are exponentially many possible operation sequences. For two strings of length 10, that's millions of possibilities. DP avoids this explosion by noticing that many of those sequences share the same sub-problems — and solving each sub-problem just once, storing the answer, so it can be reused instantly. This is what makes DP fast.

The 5 steps — follow this example

1

Set up the grid. Create a table with (m+1) rows and (n+1) columns. The extra row and column are for the "empty string" base cases.

2

Fill the base cases. d[i][0] = i (delete all i source chars to get empty). d[0][j] = j (insert all j target chars from empty). These are the known starting points everything else builds on.

3

Fill the rest, row by row. For each cell d[i][j]: if the current characters match, take the diagonal for free. Otherwise, look at three neighbours (left, above, diagonal), add 1 to each, and pick the minimum.

4

Read the answer. The bottom-right cell d[m][n] holds the minimum edit distance between the complete source and target strings.

5

Traceback (find which operations). Start at d[m][n] and walk backward. At each cell, follow whichever neighbour gave the minimum — like rewinding the decisions. Record each operation. By d[0][0], you have the full edit script.

📐 ③ The Recurrence Formula — Explained ▼
Formula

Start here — the key question at every cell

Imagine you are transforming source into target one character at a time, left to right. At some point you have handled the first i source characters and the first j target characters. You are now looking at source character S[i] and target character T[j].

The question you ask at every cell is: "What is the cheapest way to handle S[i] and T[j] right now?" There are only three real choices — and one free bonus:

↖ Match — S[i] equals T[j] (free!)

The two characters are already the same. You don't need to do anything — just move diagonally to the next pair. The cost is zero. You inherit whatever it cost to get here: d[i-1][j-1] + 0.

Example: comparing "cat" vs "car" — the 'a' at position 2 matches for free.
↖ Replace — S[i] ≠ T[j], but you swap S[i] for T[j] (cost 1)

The characters differ. You pay 1 to replace S[i] with T[j]. After this, both characters are "dealt with" — you move diagonally to the next pair. Cost: d[i-1][j-1] + 1.

Example: "cat" → "cut" — replace 'a' with 'u', then continue.
← Insert — add T[j] into source (cost 1)

You insert T[j] into source at this position. T[j] is now matched and consumed. But S[i] is still waiting — you haven't dealt with it yet. So you move left (only j decreases). Cost: d[i][j-1] + 1.

Think of it as: "I added the character T[j] needs — now I still need to handle S[i] against the rest of the target."
↑ Delete — remove S[i] from source (cost 1)

You delete S[i] — it has no matching place in the target at this position. S[i] is gone, but T[j] is still waiting. So you move up (only i decreases). Cost: d[i-1][j] + 1.

Think of it as: "S[i] is unwanted here — I remove it and still need to match T[j] against what's left of source."
💡 Why we take the minimum

We don't know in advance which of the three operations leads to the shortest overall path. So we try all three — and take the cheapest result. Because all three neighbours were computed earlier (the table fills left-to-right, top-to-bottom), we already have their costs. We simply pick the one that gives the smallest total.

The full formula

d[0][0] = 0 ← both strings empty, distance = 0 d[i][0] = i ← i source chars vs empty: delete them all d[0][j] = j ← empty vs j target chars: insert them all If S[i] equals T[j]: d[i][j] = d[i-1][j-1] ← match — move diagonally, free If S[i] differs from T[j]: d[i][j] = 1 + min( d[i][j-1], ← ← insert T[j] (move left) d[i-1][j], ← ↑ delete S[i] (move up) d[i-1][j-1] ← ↖ replace S[i]→T[j] (move diagonal) )

The arrows show which direction in the table each operation corresponds to. When you trace back from the bottom-right corner later, you follow these arrows in reverse to recover the exact sequence of operations.

🧠 ⑤ Key Concepts — Why DP Works and Why Greedy Fails ▼

✅ Optimal Substructure

What it means: The optimal solution to d[i][j] is built from optimal solutions to three smaller problems.

Why it matters: This guarantees that filling the table bottom-up always produces the globally correct answer — not just a local guess.

🔁 Overlapping Subproblems

What it means: The same cell d[i][j] is needed by multiple larger cells. Naive recursion recomputes it each time; DP stores it once.

Why it matters: This is why DP runs in O(mn) instead of O(3mn). Each of the (m+1)×(n+1) cells is computed exactly once.

↔ Symmetry Property

What it means: dist(S,T) = dist(T,S). Swapping source and target always gives the same distance.

Why it matters: Edit Distance is a true mathematical metric — it doesn't matter which string you call "source".

💾 Space Optimization

What it means: If you only need the distance (not the edit path), you can keep just 2 rows at a time instead of the full table.

Trade-off: Space drops from O(mn) to O(min(m,n)), but you lose the ability to trace back the operations.

Why does greedy fail?

A greedy algorithm makes the cheapest-looking choice at each step, one character at a time, without ever considering what comes next. This sounds reasonable — but watch what happens.

Follow this example step by step: "abc" → "cab"
❌ Greedy approach
abc → Compare 'a' vs 'c'
'a' ≠ 'c' → substitute → cbc (+1)
'b' ≠ 'a' → substitute → cac (+1)
'c' ≠ 'b' → substitute → cab (+1)
Total: 3 operations
Greedy sees each mismatch and immediately substitutes — it never looks ahead.
✅ DP optimal path
abc → insert 'c' at front
→ cabc (+1)
→ delete last 'c'
→ cab (+1)
Total: 2 operations
DP evaluates all three options at every cell and finds a smarter global path.
⚠ Why greedy is wrong here

The greedy algorithm substituted 3 times because each substitution looked like the cheapest fix at that moment. But it never considered that inserting one character and deleting another could rearrange the whole string more cheaply. DP considers all three options at every position and therefore always finds the true minimum — even when the optimal path looks counterintuitive.

This is why Edit Distance cannot be solved greedily. The globally cheapest solution sometimes requires operations that look expensive locally. Only by building up all sub-answers systematically can you guarantee the correct result.

⚠ ⑥ Common Implementation Mistakes ▼
❌ Off-by-one indexing
Using S[i] directly inside the loop. The table is 1-indexed — S[0] maps to table row 1. Always access S[i-1] and T[j-1] inside the loop.
✅ Correct
Access S[i-1] and T[j-1]. Index 0 in the table is reserved for the empty string base case.
❌ Cost 1 on a match
Setting cost=1 when characters are equal. A match is free — it costs nothing to keep a character that is already correct.
✅ Correct
cost = (S[i-1] === T[j-1]) ? 0 : 1. Only substitutions cost 1. When characters match, cost = 0.
❌ Forgetting base cases
Starting the fill loop without first initialising row 0 and column 0. Every cell depends on predecessors — without base cases the entire table produces wrong values.
✅ Correct
Always set d[i][0] = i and d[0][j] = j before the main loops begin. These are the foundation everything else builds on.
🌍 ⑦ Real-World Applications ▼
Why it matters

Edit Distance is one of the most widely deployed algorithms in software. Any time a system needs to compare strings approximately rather than exactly, Edit Distance is likely involved.

🔤
Autocorrect — When you type "teh", your phone computes the edit distance from "teh" to every word in the dictionary and suggests the one with the smallest distance ("the", distance = 1).
🔍
Spell checkers — "Did you mean…?" suggestions are dictionary words within edit distance 1 or 2 from your misspelled word. Distance 1 = one typo. Distance 2 = two typos.
🧬
DNA sequence alignment — In bioinformatics, DNA mutations are exactly the three edit operations: a substitution changes one base; an insertion or deletion adds or removes one. Edit Distance finds the minimum mutations between two sequences.
📋
Git diff — When you run git diff, Git uses a variant of edit distance to compute the minimum set of line changes between two versions. The output shows exactly which lines were added, removed, or modified.
🌐
Fuzzy search — Search engines and databases use edit distance to find near-matches. If you search for "recieve", the engine finds "receive" (distance = 1) and returns relevant results anyway.
🛡
Plagiarism detection — Tools compute edit distances between passages of text. A small distance indicates one passage is a lightly modified copy of another.
✅ Summary — Everything You Need to Remember
1.

Edit Distance counts the minimum operations. Insert, delete, or replace — each costs 1. Matches are free.

2.

d[i][j] = the distance between the first i source chars and first j target chars. The final answer is always in the bottom-right cell d[m][n].

3.

At each cell: match = take diagonal free; mismatch = take min(left+1, above+1, diagonal+1). Fill row by row, left to right.

4.

Traceback recovers the actual operations. Walk backward from d[m][n] to d[0][0], following the minimum-cost predecessor at each step.

5.

Complexity is always Θ(mn) — no exceptions. Every cell must be filled. Best, worst, and average case are identical.

6.

Greedy fails. Making the locally cheapest substitution at each step misses globally cheaper combinations. DP always finds the true optimum.

What is Edit Distance?

The Edit Distance (Levenshtein Distance) between two strings is the minimum number of operations needed to transform one string into the other.

There are only 4 cases:

The DP Matrix — what you'll see

The algorithm fills a grid called the Dynamic Programming (DP) matrix. Each cell d[i][j] stores the minimum edit distance between the first i characters of the source and first j characters of the target.

■ Source chars (left)  ·  ■ Target chars (top)  ·  ■ Match (free)  ·  ■ Substitute (+1)  ·  ╌ Traceback path (answer = 1)

The bottom-right cell always contains the final answer — the minimum edit distance between the two full strings.
